SECTION 3: IN-DEPTH STUDY GUIDE - MEMBER 1 (SYSTEM ARCHITECT)

MEMBER 1: Core System Architecture, Integration & Memory Management

Role: Architect & Lead

Primary Responsibility: System cohesion, structural design patterns, memory ownership semantics, and interactive terminal lifecycle.

1. Technical Accomplishments in Phase 1

  • Facade Design Pattern Implementation: Engineered the TrailSafetySystem class, which encapsulates the complexity of the User Management subsystem, the Graph topology subsystem, and the Rescue Team unit collection. The presentation layer (main loop) only interfaces with this single class.
  • Modern C++ Ownership & RAII: Utilized std::vector<std::unique_ptr<User>>. By applying Resource Acquisition Is Initialization (RAII), every Hiker dynamically allocated via std::make_unique is strictly owned by the system and automatically freed when the system terminates.
  • Terminal REPL Controller: Created the interactive while(true) command loop with safe stream handling (clearCin()) to eliminate the notorious newline-skipping bugs caused by mixing std::cin >> choice with std::getline(std::cin, str).

2. "Why We Used This Instead of Others" (Crucial for Viva)

Tool / Technique Used Alternative Considered Architectural Reason for Rejection of Alternative
Facade Design Pattern (TrailSafetySystem) Monolithic main() function or direct cross-class calls A monolithic architecture violates the Single Responsibility Principle (SRP) and produces tight coupling. Without a Facade, adding file persistence or Dijkstra's algorithm in Phase 2 would require rewriting the UI loop.
std::unique_ptr<User> Raw Pointers (User*) Raw pointers require manual delete in destructors, exposing the application to memory leaks and dangling pointers if exceptions occur. std::unique_ptr has zero runtime overhead over a raw pointer while guaranteeing automatic destruction.
std::unique_ptr<User> std::shared_ptr<User> std::shared_ptr introduces reference-counting overhead and atomic control block synchronization. The TrailSafetySystem has unambiguous single ownership over registered hikers; shared ownership is semantically incorrect here.
Pointer Storage in Container (vector<unique_ptr<User>>) Value Storage (std::vector<User>) First, User is an Abstract Base Class and cannot be instantiated by value. Second, storing derived objects by value in a base-type container causes Object Slicing, where derived member variables (e.g. emergencyContact) and the virtual method table pointer (vptr) are stripped away.

3. Member 1 High-Yield Viva Questions & Model Answers

Q1: "Explain how your code prevents Object Slicing when storing Hikers."
Answer: "Object slicing occurs when a derived class instance is assigned to a base class value object, copying only the base subobject and discarding derived members. We prevent this by storing std::unique_ptr<User> in our container. Pointers and smart pointers maintain indirection, preserving the complete derived Hiker memory layout and its virtual table pointer (vptr), allowing full polymorphic dispatch."
Q2: "What is RAII, and where is it demonstrated in your system?"
Answer: "RAII stands for Resource Acquisition Is Initialization. It binds the lifecycle of dynamic resources to the scope of an object. In our system, std::vector<std::unique_ptr<User>> implements RAII. When std::make_unique<Hiker> allocates heap memory, ownership is immediately assigned to unique_ptr. When the vector goes out of scope or is destroyed, every hiker object is automatically deleted without requiring manual delete calls."
Q3: "Why did you delete the copy constructor in TrailSafetySystem?"
Answer: "We explicitly marked TrailSafetySystem(const TrailSafetySystem&) = delete;. Because our class holds a collection of std::unique_ptr, which are inherently non-copyable (move-only), permitting copy construction would fail at compile-time or risk dangerous shallow copies. Deleting copy semantics enforces strict single-instance management of our system state."

2. "Why We Used This Instead of Others" (Crucial for Viva)

Tool / Technique Used Alternative Considered Architectural Reason for Rejection of Alternative
Adjacency List (unordered_map<string, vector<Edge>>) Adjacency Matrix (2D Array matrix[V][V]) Trail networks are sparse graphs (|E| << |V|^2). A matrix consumes O(V^2) memory, allocating millions of empty cells for non-existent connections. An Adjacency List uses only O(V + E) space and enables O(deg(u)) edge traversals instead of O(V).
std::unordered_map (Hash Table) std::map (Self-Balancing Red-Black BST) std::unordered_map delivers amortized O(1) constant time vertex insertion and lookup using hashing. std::map requires O(log V) for every lookup and introduces pointer-heavy binary tree overhead.
std::unordered_map Integer Array with manual string mapping Integer indexing requires an additional bidirectional mapping table (string to index and index to string), introducing code complexity and potential synchronization bugs. Hash tables natively support intuitive checkpoint names (e.g. "Base Camp").
Dijkstra's Algorithm (Phase 2) Bellman-Ford Algorithm Bellman-Ford is designed to detect negative weight cycles and runs in O(V * E). Since physical trail distances can never be negative (d > 0), Dijkstra's algorithm running in O((V+E) log V) is asymptotically and practically far superior.
Dijkstra's Algorithm Breadth-First Search (BFS) Standard BFS only calculates shortest paths in unweighted graphs (where every edge cost is 1). Since mountain trails have varying lengths (e.g., 2.5 km vs 5.1 km), BFS will produce incorrect sub-optimal routes.

3. Member 2 High-Yield Viva Questions & Model Answers

Q1: "Prove why an Adjacency List is asymptotically superior to an Adjacency Matrix for trail networks."
Answer: "In national park networks, each checkpoint connects to only 2 to 4 adjacent trails regardless of how many total checkpoints exist (|E| = k * |V| where k << |V|). In an Adjacency Matrix, space complexity is O(V^2), and finding neighbors of a node requires scanning an entire row of length V, taking O(V). In an Adjacency List, space is O(V + E) = O(V), and finding neighbors takes O(deg(V)) = O(1), providing drastic performance gains."
Q2: "How will you implement Dijkstra's Algorithm in Phase 2?"
Answer: "We will use a Min-Heap priority queue: std::priority_queue<pair<double, string>, vector<pair<double, string>>, greater<>>. We maintain a distance table initialized to infinity. Starting from the rescue base, we greedily relax adjacent edges. The priority queue extracts the minimum unvisited distance in O(log V), giving total time complexity O((V + E) log V)."
Q3: "What is the worst-case time complexity of std::unordered_map, and how is it mitigated?"
Answer: "The worst-case lookup is O(V) if severe hash collisions occur and all keys hash to the same bucket (chaining). In practice, C++ STL's std::hash<std::string> provides uniform distribution, yielding average amortized O(1) performance. Furthermore, graph vertices in trail systems rarely exceed a few thousand nodes, staying well within optimal bucket load factors."

2. "Why We Used This Instead of Others" (Crucial for Viva)

Tool / Technique Used Alternative Considered Architectural Reason for Rejection of Alternative
Abstract Base Class with Pure Virtual Methods Concrete User Class with type tags (e.g. enum Role) Using an enum type tag with switch(role) statements violates the Open-Closed Principle (OCP). Every time a new role is added (e.g. ParkRanger), every switch statement across the codebase must be modified. ABC polymorphism allows adding new roles without modifying existing code.
protected variables + Getters/Setters public member variables Public variables break Encapsulation. Any part of the application could corrupt a hiker's phone number or ID with blank or invalid strings. Mutator methods allow validation (e.g., verifying non-empty strings) before updating internal state.
Virtual Destructor (virtual ~User()) Standard non-virtual destructor If a derived object (like Hiker) is held by a base pointer (unique_ptr<User>) and deleted without a virtual destructor, the C++ standard designates it as Undefined Behavior. The derived destructor will not run, leaking derived resources.
Dynamic Polymorphism (Virtual functions / vtable) C++ Templates / CRTP (Static Polymorphism) Static polymorphism resolves types at compile-time. However, user registration happens dynamically at runtime based on terminal user input. Heterogeneous collections (mixing Hikers, Rangers, and Admins in a single vector) require runtime dynamic polymorphism.

3. Member 3 High-Yield Viva Questions & Model Answers

Q1: "Explain how the Virtual Table (vtable) and Virtual Table Pointer (vptr) work in your classes."
Answer: "When a class defines a virtual function, the C++ compiler creates a static array called the vtable containing function pointers to the virtual methods for that class. Every instantiated object of that class contains an invisible pointer called vptr pointing to this vtable. When we invoke registeredUsers[i]->displayDetails(), the runtime dereferences the object's vptr, locates the correct function address in the vtable, and executes Hiker::displayDetails() dynamically."
Q2: "What is the difference between an Abstract Class and an Interface in C++?"
Answer: "C++ does not have an explicit interface keyword like Java. An Abstract Class in C++ is any class with at least one pure virtual function (= 0). A pure interface is an abstract class with only pure virtual functions and no member variables. Our User class is an Abstract Base Class because it defines pure virtual methods while also encapsulating common concrete member variables (userId, name) to share implementation logic across derived classes."
Q3: "Why is public inheritance used for Hiker rather than private or protected inheritance?"
Answer: "Public inheritance models an 'is-a' relationship, which satisfies the Liskov Substitution Principle (LSP). This guarantees that any function or container expecting a User* or User& can transparently accept a Hiker*. Protected or private inheritance models an 'implemented-in-terms-of' relationship and prevents external polymorphic casting."

2. "Why We Used This Instead of Others" (Crucial for Viva)

Tool / Technique Used Alternative Considered Architectural Reason for Rejection of Alternative
Formatted C++ Streams (<iostream>, <iomanip>) C-style printf() / scanf() C stream functions lack type safety. A mismatched format specifier (e.g. %s for an integer) causes undefined behavior or stack corruption. C++ stream operators (<<, >>) are strictly type-safe, extensible for custom classes, and leverage RAII buffer flushing.
Plain-Text Delimited Files / CSV (Phase 3 Persistence) Binary Serialization (fwrite / reinterpret_cast) Binary serialization is platform-, endianness-, and compiler-padding dependent. A binary file compiled on 64-bit GCC will crash on 32-bit MSVC. Plain-text CSV/JSON is human-readable, portable across all operating systems, and easily auditable by park authorities.
Offline-First Architecture Cloud-Dependent Database (e.g., MySQL / Firebase) A trail safety system operates in deep mountainous terrain where internet and cellular connectivity is frequently unavailable. A cloud-dependent system would fail during a wilderness blackout. The system must operate 100% locally with optional asynchronous cloud sync.
Environment Variable Injected API Keys (Phase 4) Hardcoded API Keys in source code Hardcoding API tokens in .cpp files causes catastrophic security vulnerabilities when pushed to public GitHub repositories. Using std::getenv() loads keys from the OS environment, completely decoupling credentials from the codebase.

API Key Security Architecture (How Secrets Must Be Managed)

In industry and academia, hardcoding private API keys in version-controlled repositories is a severe security violation. Our project enforces the following security architecture:

  1. Zero Hardcoded Credentials: No API key string is ever placed inside main.cpp or any source file.
  2. Environment Variable Injection: API keys are read securely from the host operating system at runtime using standard C++ std::getenv(): 
    const char* weatherKey = std::getenv("OPENWEATHER_API_KEY");
if (!weatherKey) {
    std::cout << "[Warning] Weather API key not set. Using cached offline weather models.\n";
}
  3. .gitignore Protection: Configuration files (such as .env, secrets.json, or credentials.cfg) are explicitly listed in our .gitignore to guarantee they are never committed to GitHub.
  4. Graceful Offline Fallback: If network connectivity is unavailable or the API key is expired, the system gracefully falls back to deterministic offline simulation weights without crashing.
